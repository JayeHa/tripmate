# 라이브러리 도입 원칙

새 의존성을 판단할 때 따르는 절차다. 사람도 AI 도 같은 순서로 하고, 요약하거나 건너뛰지 않는다.

## 트리거

아래 중 하나에 해당하면 **코드를 쓰기 전에** 이 절차를 밟는다.

- 새 npm 의존성이 필요한 기능 구현
- 자체 구현 → 라이브러리 대체
- 라이브러리 → 자체 구현 대체
- **메이저 업그레이드** (0.x 는 마이너도 메이저로 본다)
- **의존성 제거**

탈출 비용이 실제로 드는 순간은 도입보다 업그레이드 · 제거 때다. 그래서 둘 다 트리거에 넣는다.

## 금지 사항

- 사용자 승인 없이 `pnpm add` · `package.json` 수정 금지
- 새 라이브러리 import 를 먼저 쓰고 나중에 설명하는 순서 금지. **판단 → 승인 → 구현** 순서를 지킨다
- 기억에 기대어 「표준이다」 「활발히 유지보수된다」고 단정 금지.
  라이선스 · 최근 릴리스 · 메인테이너 수 · peer 호환은 **직접 조회하고 출처(명령 · 날짜)를 남긴다**.
  조회할 수 없으면 `(미확인)` 으로 적고 사용자에게 확인을 요청한다
- 번들 크기는 **`next build` 전후 실측만** 쓴다. 「가볍다」 「작다」 같은 표현으로 대신하지 않는다
- 자체 구현을 권할 때 「학습 · 설계 경험」 같은 코드 바깥 이유를 근거로 쓰지 않는다.
  근거는 항상 「라이브러리가 이 환경의 X 를 받지 못한다」는 기술적 사실이어야 한다

조회 예:

```bash
npm view <pkg> license version time.modified maintainers peerDependencies   # 레지스트리
gh api repos/<owner>/<repo> --jq '{pushed_at, open_issues_count, archived}'  # 저장소 활동
```

## STEP 0 — 기존 자산 확인 (새로 들일 때 먼저)

**새 의존성 추가 · 자체 구현 → 라이브러리 대체**일 때만 거친다. 메이저 업그레이드 · 제거 · 라이브러리 → 자체 구현은
대상이 이미 설치돼 있어 첫 질문이 늘 Yes 가 되므로 STEP 0 을 건너뛰고 STEP 1 부터 시작한다.

`package.json` 과 코드베이스를 실제로 열어 보고 답한다.

- [ ] 이미 설치된 라이브러리로 해결되는가?
- [ ] `shared/lib` 의 유틸 · 훅으로 해결되는가? (예: `usePointerDrag` · `useDebouncedValue` · `useMediaQuery`)
- [ ] 비슷한 문제를 코드베이스가 이미 다르게 풀고 있는가? 있으면 그 방식을 따를지 먼저 판단한다

**하나라도 Yes 이고 그것으로 해결하기로 하면 여기서 끝낸다.** 새 의존성을 제안하지 않는다.
기존 방식이 이번 요구를 못 받는다고 판단하면 그 이유를 한 문장으로 적고 STEP 1 로 간다.

## STEP 1 — 도입 여부 판단

### 경로 나누기 (먼저 판정)

**경량 경로** — 아래를 **모두** 만족하면 3줄로 끝낸다.

- 탈출 비용이 낮다 (교체할 때 고칠 곳이 유틸 1~2 파일이나 설정 파일 하나)
- 전역 동작을 가로채지 않는다 (프로바이더 · 인터셉터 · 빌드 설정에 끼어들지 않음)
- 대안 비교가 사실상 의미 없는 표준 도구다

개발 도구(eslint 플러그인 · prettier 플러그인 · 테스트 유틸)는 번들에 들어가지 않으므로 보통 여기에 해당한다.

출력: `문제 / 선택 / 탈출 비용` 3줄. 이것도 ADR 로그에 남긴다.

**중량 경로** — 위 조건 중 하나라도 어긋나면 아래 5축을 모두 평가한다.

### 5축

| 축             | 묻는 것                                             | 위험 신호                                                     |
| -------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| 1. 전제 충족   | 라이브러리가 가정하는 환경 조건을 우리가 만족하는가 | SSR · RSC 경계, 비표준 응답, 브라우저 전용 API 등이 가정을 깸 |
| 2. 제어 범위   | 가져가는 통제권이 내 문제 범위보다 크지 않은가      | API 일부만 필요한데 전역(프로바이더 · 루트 레이아웃)에 붙음   |
| 3. 탈출 비용   | 교체할 때 몇 개 파일이 바뀌는가                     | 도메인 타입 · 폴더 구조가 라이브러리 모양을 따라감            |
| 4. 실패 소유권 | 장애가 나면 소스를 읽고 고칠 수 있는 크기인가       | 이슈를 올리고 기다리는 것 말고는 방법이 없음                  |
| 5. 총비용      | 초기 구현이 아니라 **계속 유지보수하는** 비용       | 자체 구현하면 엣지 케이스 발굴 · 문서화가 전부 한 사람 몫     |

> **환경 전제**: 개발자 1인. 자체 구현의 유지보수 비용은 나눠지지 않고 전부 한 사람에게 돌아온다.
> 그래서 **동점이면 라이브러리 쪽으로 기운다.** 자체 구현은 5축 중 최소 하나에서 분명한 실패 근거가 있어야 한다.

### 출력 형식 (고정)

```
[도입 판단]
전제 충족  : ✅/⚠️/❌ — 한 줄 근거
제어 범위  : ✅/⚠️/❌ — 한 줄 근거
탈출 비용  : 낮음/중간/높음 — 교체할 때 영향 범위
실패 소유권: ✅/⚠️/❌ — 대략 규모
총비용     : 라이브러리 / 자체 구현 — 어느 쪽이 싼가

권장: [라이브러리 도입 | 자체 구현 | 하이브리드]
근거: 1문장
```

### 하이브리드를 항상 후보에 넣는다

「전부 빌린다 / 전부 만든다」 두 가지로 좁히지 않는다. 대부분의 답은 **표준 문제는 라이브러리에 맡기고, 도메인 고유 요구만 그 위에 얹는 것**이다.

```
도메인 API 층   ← 우리가 설계 (이름, 반환 타입, 정책)
라이브러리 층   ← 표준 문제 (마운트 · 생명주기 · 브라우저 차이)
```

## STEP 2 — 라이브러리 고르기 (도입이 정해진 뒤)

**후보 하나만 내밀지 않는다.** 최소 2개를 비교하고 권장안을 낸다.

### 필수 게이트 — 하나라도 실패하면 탈락

- [ ] 라이선스 (MIT · Apache · ISC · BSD 계열)
- [ ] React 19 · Next 16 호환 (`peerDependencies` 를 조회한다)
- [ ] 타입 지원 (내장 / `@types` 별도 / 부실)
- [ ] 유지보수 신호 — 최근 릴리스, 이슈 응답, 메인테이너 수(1명이면 ⚠️)

각 항목에 조회한 출처를 붙인다. 조회하지 못한 항목은 `(미확인)`.

### 비교 축

- 인터페이스 미스핏: 라이브러리 모델과 우리 도메인 모델의 거리
- 의존성 트리 깊이 · 번들 크기 (`next build` 실측)
- **escape hatch**: 라이브러리가 안 해 주는 것을 저수준 API 로 우회할 수 있는가 ← 가장 자주 발목 잡히는 축
- 생태계: 문제가 생겼을 때 사례가 검색되는가

### 출력 형식 (고정)

```
[후보 비교]
| 축           | A   | B   |
| ------------ | --- | --- |
| 게이트       | ... | ... |
| 미스핏       | ... | ... |
| escape hatch | ... | ... |
| 번들/의존성  | ... | ... |

권장: A
근거: 1문장
포기하는 것: 1문장
```

## STEP 3 — 스파이크 (가장 어려운 경우로 검증)

**README 데모로 검증했다고 말하지 않는다.** 모든 라이브러리는 데모에서 잘 돈다.

1. 우리 환경에서 **가장 어려운 경우 1개**를 지목한다
2. 그 경우만 실제로 붙여 본다
3. 받아지지 않는 지점이 나오면 그게 자체 구현이나 다른 후보의 근거가 된다

> 가장 어려운 경우 예: 다른 컨테이너로 옮기기, 터치 · 키보드 입력, SSR 하이드레이션 경계, 오프라인 큐, 실시간 동기화와의 충돌

**AI 가 확인할 수 없는 부분은 그렇다고 적는다.** 지도 타일 · 애니메이션 · 터치 감각처럼 화면을 보거나 손으로 만져야 아는 것은
스파이크 결과에 「사용자 확인 필요」 와 확인할 항목을 남긴다. 보지 않은 것을 확인했다고 쓰지 않는다.

## STEP 4 — 어댑터 경계

라이브러리를 직접 부르는 곳을 모아서, 교체할 때 고칠 범위를 좁힌다. FSD 레이어에 맞춰 이렇게 둔다.

| 종류                               | 경계                                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 데이터 · 계산 (날짜, 공휴일, 파서) | `shared/lib` 이나 entity 의 `api` 에 **한 파일**. 밖에서는 우리 함수 이름만 쓴다 (예: `shared/lib/holidays.ts`)   |
| 외부 서비스 API                    | entity 의 `api` 나 Route Handler 한 곳. 응답은 우리 타입으로 바꿔서 내보낸다                                      |
| UI 라이브러리 (지도, 드래그앤드롭) | **사용하는 곳을 한 슬라이스로 제한**한다. 그 슬라이스 밖으로는 라이브러리 타입을 내보내지 않고 우리 타입만 보인다 |

UI 라이브러리는 컴포넌트 트리에 직접 붙어서 「호출부가 이름을 모르게」 감싸면 오히려 래퍼가 라이브러리 API 를 다시 만들게 된다.
그래서 이름을 숨기는 대신 퍼지는 범위를 막는다.

**예외 — 앱 전역 provider.** 라이브러리가 루트에 provider 를 요구하면(`APIProvider`, `QueryClientProvider`) 그 한 줄은 `app` 레이어(`app/providers.tsx`)에 둔다.
provider 는 성격상 슬라이스 안으로 옮길 수 없다. 이 경우에도 provider 를 뺀 나머지 사용처는 위 기준대로 모은다.

## STEP 5 — 결정 기록 (ADR 5줄)

도입과 미도입 **양쪽 모두** 아래 로그에 남긴다. 채택하지 않은 이유가 나중에 가장 값진 자료가 된다.

```
- 문제:
- 후보:
- 선택:
- 근거:
- 포기한 것 / 재평가 트리거:
```

## 버전 범위

- 기본은 `^` + lockfile. CI 가 `pnpm install --frozen-lockfile` 로 설치 결과를 고정한다
- **0.x 도 `^` 그대로 둔다.** semver 에서 `^0.y.z`(y ≥ 1)는 이미 `0.y` 안에서만 움직여(`~` 와 같음) 깨지는 변경을 받지 않는다.
  `@electric-sql/pglite` 의 `~0.3.16` 은 `^0.3.16` 과 같은 범위다
- **프레임워크 코어는 정확한 버전으로 고정하고 함께 올린다.** `next` · `eslint-config-next`(16.3.6), `react` · `react-dom`(19.2.8).
  서로 맞물려 배포되고, 초기 설정부터 이렇게 고정돼 있다
- `typescript-eslint` 는 8.70.1 로 정확히 고정돼 있다. 코드 규칙 PR(#43)에서 넣었고 고정한 이유는 기록이 없다.
  `eslint-config-next` 도 `^8.46.0` 으로 같은 패키지를 끌어오며, 지금은 한 벌만 설치된다. 다음 업그레이드 때 `^` 로 풀지 판단한다
- 그 밖에 범위를 좁히거나 정확히 고정하는 것은 이유를 ADR 에 적는다
- 범위를 넘는 업그레이드는 트리거의 「메이저 업그레이드」 로 다룬다

## 한 줄 원칙

> 전제가 깨지지 않으면 빌린다. 빌리되 경계는 내가 긋는다.
> 빌리지 않기로 했으면 그 이유를 **기술적 사실 한 문장**으로 말할 수 있어야 한다.
> 말하지 못하면 그건 결정이 아니라 취향이다.

- **후보**: Routes API(`computeRoutes`)로 구간마다 계산 / 직선거리(haversine)로 추정하고 실제 경로는 구글맵 링크로 넘기기.

- **포기한 것 / 재평가 트리거**: 정확한 소요 시간을 포기한다. 사용자가 추정치가 틀린다고 느끼거나, 실제 경로가 필요한 기능(경로 지도 #14)에서 다시 판단한다. 별도 지도 화면(`views/trip-map`)은 지금도 Routes API 를 쓴다(`entities/schedule-item/api/compute-day-route.ts`).
